## Open questions

Things the code does not settle and that need the author or a document to answer.

### `lms_baffle`

- {mod}`lms_baffle`: the plate scale ``scale = 0.0013`` arcsec/pixel is hard-coded (a commented alternative ``1.6 / nrc`` suggests a 1.6 arcsec field); the provenance of the value and of ``APP_METIS_PSF.fits`` is not recorded.
- {mod}`lms_baffle`: the IFU field is drawn as 0.577 x 0.897 arcsec offset by 0.055 arcsec in x, which does not match ``Globals.alpha_fov`` (0.897) x ``Globals.beta_fov`` (28 x 20.7 mas = 0.580) in orientation or offset; it is unclear which axis is alpha.

### `lms_detector`

- {py:obj}`lms_detector.Detector.down_sample`: if ``n_rows`` or ``n_cols`` is not a multiple of ``s`` the ``reshape`` raises ``ValueError``; there is no check or padding.

### `lms_efficiency`

- {mod}`lms_efficiency`: no design document is cited for the constants (mirror reflectivity 0.99, ZnSe transmission 0.98, blaze peak 0.75, angular width 0.23, reflection counts 4+4+5+6).  Their provenance should be confirmed with the author before the model is used for anything quantitative.
- {py:obj}`lms_efficiency.Efficiency.slow`: the reflection counts and coating values are not referenced to any document.

### `lms_filer`

- {py:obj}`lms_filer.Filer.read_mosaic`: for ScopeSim data detector 2 is placed at index 0 and detector 1 at index 1, the reverse of the ToySim ordering and of the irdb layout (``x_cen`` = -19.547 mm for detector 1).  Whether ScopeSim numbers its detectors differently from the irdb table should be checked with a real ScopeSim frame.
- {py:obj}`lms_filer.Filer.read_pinholes`: the default filter is ``|x| < 1.6``, ``|y| < 2.7`` mm while the EFP half-field is 2.48 mm along x and 1.60 mm along y (``Globals.efp_x_fov_mm`` / ``efp_y_fov_mm``); the two limits look transposed.
- {py:obj}`lms_filer.Filer.read_pinholes`: the relative ``./inst_pkgs`` path resolves only when the ScopeSim instrument packages have been downloaded into ``src/``.

### `lms_globals`

- {mod}`lms_globals`: ``efp_mm_wcu_as`` (4.538 mm per WCU arcsec) is not the inverse of ``efp_arcsec_mm`` (5.533 mm per EFP arcsec); the WCU mask files therefore appear to use a different angular scale from the EFP.
- {mod}`lms_globals`: ``efp_x_fov_mm`` = 4.963 mm, while the in-line comment quotes ray-trace bounds of 5.842 mm (x) and 3.208 mm (y); only y agrees.
- {mod}`lms_globals`: ``debug_level`` defaults to ``'high'`` at import; every program overrides it with :meth:`Globals.set_debug_level`.
- {py:obj}`lms_globals.Globals.make_lms_config_id`: the prism-angle tag uses ``abs()`` with no sign character, so negative and positive prism angles map to the same identifier.

### `lms_ipc`

- {mod}`lms_ipc`: the IPC coupling of 1.3 % is attributed to "Rauscher"; the diffusion width to "Hardy et al. 2014"; the 3.3 % corner loss has no reference.  No wavelength dependence is modelled.
- {py:obj}`lms_ipc.Ipc.make_intra_pixel_transmission_screen`: with ``oversampling = 4`` the border is 12 of 16 sub-pixels, so the mean pixel transmission is ``1 - 0.033 * 12 / 16 = 0.975``, not ``1 - 0.033``; whether the 3.3 % figure is meant per border sub-pixel or per pixel is not documented.
- {py:obj}`lms_ipc.Ipc.add_ipc`: the coupling is not subtracted from the central pixel; flux conservation is restored only by the global renormalisation in :meth:`make_kernel`, so the effective central-pixel fraction is slightly lower than ``1 - 4 * ipc_factor``.
- {py:obj}`lms_ipc.Ipc.apply`: the screen tiling assumes detector pixel boundaries coincide with image pixel ``0, os, 2os, ...``; :class:`lmsiq_test.Test` places a source across such a boundary to check this.

## Inconsistencies

Places where two parts of the code, or the code and the instrument description, disagree.

### `lms_baffle`

- {mod}`lms_baffle`: ``Analyse()`` is instantiated only for the side effect of setting ``Analyse.fwhm_sigma``, which :meth:`lmsiq_analyse.Analyse.exact_rectangular` does not need.

### `lms_detector`

- {mod}`lms_detector`: ``Detector.mosaic_gap`` is 2.23 mm whereas ``Globals.det_gap`` is 3.0 mm; the two constants describe the same inter-detector gap and are used in different parts of the package (the irdb uses 2.23 mm).
- {mod}`lms_detector`: the original module docstring read "Inter pixel capacitance object", which describes :mod:`lms_ipc`, not this module.
- {class}`lms_detector.Detector`: ``mosaic_gap`` (2.23 mm) disagrees with ``Globals.det_gap`` (3.0 mm).
- {py:obj}`lms_detector.Detector.get_bounds`: uses ``Detector.mosaic_gap`` (2.23 mm); the affine transforms in :mod:`lms_transform` use ``Globals.det_gap`` (3.0 mm).
- {py:obj}`lms_detector.Detector.down_sample`: the block *mean* is used, so ``down_sample`` does not conserve flux; the docstring of the original called this "measuring" an observation.
- {py:obj}`lms_detector.Detector.detect`: the original docstring described a returned mosaic dictionary with 'images', 'cartoons' and 'reads' entries; the method returns a single array.

### `lms_efficiency`

- {mod}`lms_efficiency`: the ``wave`` argument of ``Efficiency.slow`` is unused; the "slow" transmission is wavelength independent.
- {py:obj}`lms_efficiency.Efficiency.slow`: ``wave`` is accepted but ignored.
- {py:obj}`lms_efficiency.Efficiency.blaze`: the previous docstring described the model as ``eff_max cos(k x echelle_angle)``; the implementation is a sinc-squared profile.
- {py:obj}`lms_efficiency.Efficiency.test`: ``n_orders = omax - omin`` and ``arange(omin, omax)`` drop the highest order returned for ``w_test_lim[0]``.
- {py:obj}`lms_efficiency.Efficiency.test`: the ``amin`` / ``amax`` echelle angles returned by ``Wcal.find_echelle_setting`` are immediately replaced by the fixed values -6.0 and +6.0.

### `lmsiq_analyse`

- {mod}`lmsiq_analyse`: :meth:`Analyse.eed` accepts but ignores a ``normalise`` keyword that :mod:`lmsiq_cuber` passes as ``'to_average'``; the curves are always normalised by the image total.
- {py:obj}`lmsiq_analyse.Analyse.extract_cube_strips`: the band is centred on the geometric image centre, not on the PSF centroid.
- {py:obj}`lmsiq_analyse.Analyse._gauss`: no constant/baseline term, so a profile with a non-zero background biases the fitted FWHM upward.  The pipeline's ``drl.lines.fit_gaussian`` includes a baseline.
- {py:obj}`lmsiq_analyse.Analyse.get_dispersion`: consecutive rays in the series are not guaranteed to be adjacent in x, so individual ``dw/dx`` differences can be noisy or of either sign; only the interpolated value at ``wave`` is used.

- {py:obj}`lmsiq_analyse.Analyse.find_fwhm_multi`: the error flag in both tuples is hard-wired ``False`` even if every image failed (in which case ``np.mean`` of an empty array returns ``nan`` with a warning).
- {py:obj}`lmsiq_analyse.Analyse.find_fwhm`: ``rc_lo`` is computed from ``n_cols`` for both axes, so the method assumes a square image; the band is centred on the image centre, not the PSF centroid.
- {py:obj}`lmsiq_analyse.Analyse.find_fwhm`: :meth:`lmsiq_phase.Phase.process` calls this with ``oversample = 4`` on an already down-sampled image, which scales the FWHM by 1/4 and widens the band to 9 detector pixels.
- {py:obj}`lmsiq_analyse.Analyse._fit_gaussian`: the error-path ``covar`` shape (4, 3) does not match the success-path (3, 3).
- {py:obj}`lmsiq_analyse.Analyse._fit_gaussian`: the FWHM guess of 2.0 is in whatever units ``x`` carries (detector pixels after rescaling, image pixels otherwise).
- {py:obj}`lmsiq_analyse.Analyse._find_fwhm_lin`: using the first and last samples above half maximum makes the width sensitive to noise spikes or secondary maxima (any wing sample above ``yh`` extends the FWHM); the method is intended for smooth model PSFs.
- {py:obj}`lmsiq_analyse.Analyse.find_phot`: the default ``method`` value ``'fixed_aperture'`` matches neither branch, so calling without ``method`` silently returns 0.0.
- {py:obj}`lmsiq_analyse.Analyse.find_stats`: the row range ``1:12`` is hard-coded and tied to the legacy 21-step shift grid.  Unused at HEAD.
- {py:obj}`lmsiq_analyse.Analyse.fix_offset`: the row blocks are hard-coded for a legacy 40+ step shift scan; rows 0-2 and 20-22 are untouched.  Unused at HEAD.
- {py:obj}`lmsiq_analyse.Analyse._find_mean_centroid`: a common centroid means the per-model LSFs in :meth:`lsf` include any model-to-model centroid shift as an apparent broadening or offset.
- {py:obj}`lmsiq_analyse.Analyse.find_strehls`: the profile is a single column through the brightest pixel of a 32-row x (2*slice_radius + 7)-column pseudo-cube plane whose columns are slices, so the 'peak' is the along-slice profile of the brightest slice.
- {py:obj}`lmsiq_analyse.Analyse.find_strehls`: ``np.argmax(image, keepdims=True)`` returns a (1, 1) array so ``rmax``, ``cmax`` are arrays; indexing still works after ``np.squeeze``.
- {py:obj}`lmsiq_analyse.Analyse.eed`: the ``normalise='to_average'`` keyword passed by :meth:`lmsiq_cuber.Cuber.build` is never read; curves are always normalised by the image total.
- {py:obj}`lmsiq_analyse.Analyse.eed`: for the pseudo-cube, x is the slice index and y the along-slice detector row, so ``'across-slice'`` EE is measured in units of slices (20.7 mas) and ``'along-slice'`` in detector pixels (8.7 mas); the rectangular aperture's fixed dimension ``2 * r_max`` is the same number in both cases even though the cube is far from square (32 rows x ~15 columns).
- {py:obj}`lmsiq_analyse.Analyse.find_ee_axis_references`: the input tuple layout matches the legacy :meth:`lmsiq_summariser.Summariser.read_profiles` output, not :meth:`eed`; unused at HEAD.
- {py:obj}`lmsiq_analyse.Analyse.ycompress`: the ``+ 0.5`` column centre offset, combined with the ``pco = 0.5`` convention in :meth:`exact_rectangular`, places the aperture on pixel boundaries rather than pixel centres.
- {py:obj}`lmsiq_analyse.Analyse._boxcar`: the window ``[i - hw, i + hw)`` is asymmetric (one more sample on the low side) and its width is ``2 * hw`` rather than ``box_width``.
- {py:obj}`lmsiq_analyse.Analyse.lsf`: with ``u_radius='all'`` the aperture centres run from ``centroid - (n-1)/2`` to ``centroid + (n-1)/2`` and so extend past the image edge whenever the centroid is off-centre; :meth:`exact_rectangular` clips them.
- {py:obj}`lmsiq_analyse.Analyse.lsf`: for the pseudo-cube, ``axis = 0`` is *across* slices (x = slice index) while for the raw Zemax image ``axis = 0`` is the spectral direction; ``Cuber.build`` stores the former under ``'acr_'`` and the latter under ``'lsf_'`` keys.
- {py:obj}`lmsiq_analyse.Analyse.exact_rectangular`: after clipping, ``fc2 = x2 - c2`` can exceed 1 when the aperture extends past the last column.

## Bugs

Behaviour that is wrong as written. Documented, not fixed.

### `lms_baffle`

- {py:obj}`lms_baffle.main`: ``np.log10(image)`` is evaluated on the raw image without clipping, so zero or negative pixels produce ``-inf``/``nan`` with runtime warnings.
- {py:obj}`lms_baffle.main`: ``Plot.set_plot_area('FP1 APP PSF')`` passes a positional argument to a ``**kwargs``-only method in :mod:`lmsdist_plot`, which raises ``TypeError``. ### `lms_detector`

- {mod}`lms_detector`: :meth:`Detector.detect` adds ``rng.poisson(sqrt(image))`` to the image instead of replacing the image by ``rng.poisson(image)``; this biases the mean signal upward by ``sqrt(signal)`` and gives the wrong variance.
- {py:obj}`lms_detector.Detector.detect`: ``shot = rng.poisson(np.sqrt(image))`` is *added* to ``image``.  A correct shot-noise realisation is ``image = rng.poisson(image)``; the current code biases every pixel upward by about ``sqrt(signal)`` and gives the wrong variance.  Not used by ``lmsiq``; used by ``lmssim``.

### `lms_efficiency`

- {py:obj}`lms_efficiency.Efficiency.test`: the angle scan includes ``ang == 0.0`` only if 50 samples over [-6, 6] land exactly on zero (they do not, the step is 12/49), so the ``ZeroDivisionError`` in :meth:`blaze` is avoided by accident.
